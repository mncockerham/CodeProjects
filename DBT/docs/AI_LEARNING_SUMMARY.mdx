## 🧠 Core Concepts Explored
We focused heavily on the **Paradigm Shift** from Airflow to Dagster/dbt:
1.  **Transform vs ELT:** Established that dbt only handles the **"T" (Transform)**. It compiles SQL SELECTs into physical materializations (Tables/Views). For tasks like `COPY` or `UNLOAD`, separate ingestion tools or Python operators inside orchestrators should be used.
2.  **Tasks vs Assets:** Contrasted Airflow's "Task-based" orchestration (running scripts) with Dagster's declarative "Asset-based" orchestration (guaranteeing physical state). 
3.  **The "Materialize" Concept:** Discussed why "Materialize" is used instead of "Run." While running a python script just executes code, telling Dagster to "Materialize" triggers built-in metadata tracking (rows affected, column schemas, execution time) and draws visual lineage natively without custom boilerplate code.
4.  **I/O Managers:** Discussed how Dagster's Asset system eliminates the need for clunky Airflow XComs by automatically serializing/deserializing Pandas DataFrames to the disk between execution steps.

## 🤔 Key Questions Addressed
*   *How is dbt usually scheduled?* -> Usually via Data Orchestrators (Airflow/Dagster), dbt Cloud, or CI/CD pipelines.
*   *Do Dagster or Prefect have free Mac installs?* -> Yes, both run highly capable local UI servers using standard `pip` installs and local SQLite states. We installed Dagster natively.
*   *Is "Materialized" just a fancy way of saying run?* -> It triggers a run (`dbt build`), but functionally guarantees the *state* of the data asset and collects native observability metadata, whereas a "run" in Airflow simply triggers a script that may or may not succeed conceptually.
*   *Does dbt support COPY/UNLOAD commands?* -> No, that is the Extracts/Loads portion (Airbyte, Fivetran, Python extractors). dbt expects the data to already be loaded. We successfully modeled an ELT pipeline using Dagster to extract/load into DuckDB, with dbt acting purely as the T aggregator.
